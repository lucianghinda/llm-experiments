The defect is a **check-then-act race** in [Checkout#charge](/workspace/lib/checkout.rb:48). The mutex protects individual store operations, but nothing reserves the order between lookup and charging. I ran the supplied test: it passes by asserting **two gateway calls and two payment records**.

1. **Concrete interleaving**

   | Step | Request A | Request B |
   |---|---|---|
   | 1 | Looks up order 41; finds nothing | |
   | 2 | | Looks up order 41; finds nothing |
   | 3 | Calls gateway with `order-41` | |
   | 4 | | Calls gateway with `order-41` |
   | 5 | Inserts payment | |
   | 6 | | Inserts another payment |

   Both calls use the same key, but [FakeGateway#charge](/workspace/lib/checkout.rb:35) records every invocation without deduplication. The parameter name `idempotency_key` establishes no protection. The code proves duplicate gateway invocations; any real provider’s behavior is unspecified.

2. **Smallest production-worthy correction**

   Persist a payment attempt **before calling the gateway**, with a database `UNIQUE(order_id)` constraint and a status such as `pending`, `succeeded`, or `unknown`.

   - Atomically insert the attempt and establish which request owns execution. Commit this reservation before making the external call.
   - Only the request that successfully created the reservation may call the gateway. A uniqueness conflict means load the existing attempt; it does not grant permission to charge.
   - Persist the gateway result and transition to `succeeded` after a confirmed response. Existing pending or unknown attempts must not trigger another charge.

   In this reproduction, the equivalent is a store method that checks and inserts under **one mutex acquisition**, returning both the attempt and whether this caller created it. Production needs database enforcement across processes.

   Adding uniqueness only to the existing final insert is too late: both gateway calls have already happened. Likewise, a database transaction cannot roll back an external charge; rolling back the reservation after an uncertain gateway outcome would reopen the duplicate-charge path.

3. **Retries and regression test**

   A retry should return the stored successful result, or report that the existing attempt is pending/unknown. A timeout or crash after dispatch must not cause an automatic second gateway call—even with the same key. Resolve uncertainty through reconciliation or a verified provider capability; neither is supplied here. A pending record must not be presented as proof of payment.

   Adapt the [existing barrier test](/workspace/test/checkout_test.rb:5): hold both requests after their initial missing lookup, then release them to compete for the atomic reservation. Assert **one gateway invocation and one attempt record**. After both complete, retry once more and assert the gateway count remains one and the stored successful result is returned. This deterministically fails for the current implementation.

4. **Limitation**

   This provides at-most-once dispatch for an order, at the cost of potentially stranded attempts. A crash after reservation but before dispatch can leave an unpaid order pending; a crash after charging but before recording success can leave a paid order pending. Automatically expiring and reclaiming such attempts is unsafe without additional guarantees. The supplied gateway offers no way to resolve that ambiguity, so an exactly-once, automatically recovering solution cannot be established from this code alone.
