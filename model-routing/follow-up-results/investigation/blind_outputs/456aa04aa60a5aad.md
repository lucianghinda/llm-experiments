`Checkout#charge` performs a check-then-act sequence: it looks up a payment, calls the gateway, and only then inserts a record. The store locks each lookup and insert separately, but the whole sequence is not atomic. Both requests can therefore observe “no payment” before either inserts.

A concrete interleaving is:

1. Request A looks up order 41 and finds nothing.
2. Request B looks up order 41 and finds nothing.
3. Both pass the `after_lookup` seam.
4. A calls the gateway and inserts a payment.
5. B calls the gateway and inserts another payment.

The test demonstrates this schedule: the gateway receives two charge calls and the store ends with two records, despite both calls using the same provider key. The code does not establish that the gateway deduplicates that key, so it cannot be relied on to prevent the duplicate charge.

**Smallest production-worthy correction:** make the database enforce one payment per order with a unique index on `order_id`, and make creation a single atomic claim/insert operation. A transaction around “find, call gateway, insert” alone is insufficient unless it also serializes contenders for the order. For example, atomically create or claim a payment row under the unique constraint; only the request that successfully claims it may initiate the charge. Concurrent requests should load and follow that same row rather than create another one. The claim and its uniqueness must be enforced by the database, not just by a Ruby mutex, since requests may run in different processes.

Retries should use the existing order-derived key consistently and consult the persisted payment/claim state before starting another charge. If a request times out or loses its response after calling the gateway, the service cannot infer from this code whether the charge succeeded. It should retain the claim and reconcile or retry using the same key; it must not create a fresh claim or key for the same order. Safe resolution of that uncertain outcome depends on behavior the supplied code does not specify.

A focused regression test would run two threads for one order, force both to contend at the claim step, then assert that only one gateway call occurs and only one payment row exists. The current test’s assertions of two calls and two rows would fail under the corrected behavior.

**Tradeoff:** a claim can remain unresolved if the process fails after claiming but before recording the gateway result. Recovery then needs a defined pending/unknown state and reconciliation policy. The unique index prevents duplicate local payment rows; by itself it cannot guarantee exactly-once charging at the gateway.
