1. **The race is “check, charge, insert.”** In [Checkout#charge](/workspace/lib/checkout.rb:48), observing no payment is treated as permission to charge. The store synchronizes individual operations, but that whole sequence is not atomic.

   A concrete execution for order 41:

   | Step | Request A | Request B |
   |---|---|---|
   | 1 | Lookup returns nothing | |
   | 2 | | Lookup returns nothing |
   | 3 | Calls gateway with `order-41` | |
   | 4 | | Calls gateway with `order-41` |
   | 5 | Inserts payment | |
   | 6 | | Inserts another payment |

   The stable key does not establish deduplication: [FakeGateway#charge](/workspace/lib/checkout.rb:35) records every call, including repeated keys. The supplied test reproduces this exact race; I ran it successfully.

2. **The smallest defensible correction is a durable, exclusive claim before calling the gateway.** Add a payment state and a database `UNIQUE(order_id)` constraint, with `order_id` non-null.

   In a short transaction, attempt to insert the payment with its stable provider key and state `in_progress`. Commit that claim **before** making the gateway call. Only the request that created the claim may call the gateway. A conflicting request reads the existing payment and returns its current state.

   After a successful gateway response, persist the result and mark the payment successful in another transaction. An existing row must no longer automatically mean success.

   The claim’s creation and acquisition of permission to dispatch must be atomic. A database uniqueness conflict must be handled as “another request owns this order.” For this reproduction, an atomic insert-if-absent under the store mutex models that operation; production coordination must work across processes.

   Adding uniqueness only to the current final insert is insufficient: both gateway calls have already happened. Locking a lookup that finds no payment also does not establish an exclusive claim.

3. **An uncertain response must preserve uncertainty.** If the gateway times out, or the process dies after dispatch but before recording success, retain the claim. Subsequent checkout retries return pending/unknown status without issuing another charge. They must not delete the claim, generate another key, or treat its presence as proof of success.

   A focused regression test can retain the supplied two-thread barrier immediately after both initial lookups, before the atomic claim. Release both callers, join them, then retry the checkout once. Assert:

   - Exactly one gateway invocation occurred.
   - Exactly one payment exists.
   - The payment is successful after the winning request completes.
   - The subsequent retry caused no additional invocation.

   The current implementation fails the first two assertions. Keep the barrier before claim acquisition so the corrected implementation does not deadlock waiting for two winners.

4. **The tradeoff is availability after uncertainty.** This provides at-most-once dispatch by the service, but a crash after committing the claim and before contacting the gateway can leave an unpaid order stuck pending. Automatically reclaiming that attempt could duplicate a charge if dispatch actually occurred.

   No local database transaction can atomically commit a remote charge and its local record. Safe automatic recovery requires an explicitly established provider deduplication or reconciliation capability; the supplied code establishes neither. Until then, uncertain attempts require reconciliation rather than blind retries.
