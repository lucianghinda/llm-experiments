The race is in the **find-then-charge-then-insert** sequence in `Checkout#charge`. `find_by_order` and `insert` each lock their own short operation, but there is no lock or transaction covering the whole sequence. Both requests can therefore observe “no payment,” call the gateway, and only afterward record a payment. The test’s barrier forces exactly that interleaving.

A concrete timeline for order 41:

1. Request A finds no payment.
2. Request B finds no payment.
3. Both pass the barrier and call `gateway.charge` with `order-41`.
4. Both insert a payment row.

The matching provider key does not prevent this in the supplied code: `FakeGateway` records each call, and `PaymentStore` permits duplicate order IDs.

**Smallest production-worthy correction:** make claiming an order’s payment slot atomic, backed by a database unique constraint on `payments.order_id`. For example, insert a pending payment row with a stable provider key using an atomic insert-or-fetch operation; only the request that successfully creates the row proceeds to the gateway. A transaction around “check, then insert” alone is insufficient under ordinary concurrent isolation unless it also locks a shared row or uses a uniqueness constraint to resolve the race. The unique constraint is the final safeguard against two claims.

On a retry, return or resume the existing payment record and use its persisted provider key; do not create a new key or blindly issue another charge. If the first request’s response is uncertain, the code alone does not establish whether repeating a gateway call with the same key is safe. That depends on an unstated provider contract, so the service must not assume it. It should preserve the pending/uncertain state and reconcile or retry only according to a verified provider capability.

**Focused regression test:** run two threads for the same order with a barrier after both attempt to claim it. Assert that only one request becomes the gateway caller and only one payment record exists. The current test demonstrates the defect by asserting two calls and two rows; the corrected test should assert one of each.

**Tradeoff:** this prevents overlapping requests from independently claiming the same order, but it does not by itself guarantee exactly-once charging across a crash or lost response between the gateway call and recording its result. Resolving that case requires durable payment states plus provider-supported idempotency or reconciliation behavior; neither is specified by this reproduction.
