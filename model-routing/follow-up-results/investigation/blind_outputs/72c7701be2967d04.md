The failure is a **check-then-act race** in [Checkout#charge](/workspace/lib/checkout.rb): finding no payment does not reserve the order. Each store method is synchronized individually, but the lookup, gateway call, and insert are not one atomic operation.

A concrete execution for order 41 is:

1. Request A looks up order 41 and finds no payment.
2. Request B looks up order 41 and also finds no payment.
3. A and B each call `gateway.charge`, both with `order-41`.
4. A and B each insert a payment row.

The shared key alone does not prevent the duplicate in this reproduction: `FakeGateway` records every call and provides no deduplication behavior. The existing test deliberately forces this timeline and observes two calls and two rows.

A production correction should first **atomically claim the order**, before calling the gateway. Add a unique database constraint on `payments.order_id`, and insert a payment record in a `pending` state in a transaction. Only the request that successfully creates the claim may call the gateway; a concurrent request that loses the insert race loads the existing record and returns its completed result or reports that it is still pending. After a successful gateway response, persist the result and mark the record complete. The uniqueness constraint is essential: a transaction around a lookup and insert alone does not necessarily prevent both requests from observing an absent row.

For an uncertain response—such as a timeout after the gateway call may have reached its destination—leave the record in an **unknown/pending** state. A retry must reuse that record and its stable `order-41` key; it must not blindly issue another charge. Recovery requires a supported way to determine the first call’s outcome, or a documented gateway guarantee that retrying with the same key is safe. Neither is established by the supplied code, so the service cannot safely promise automatic recovery from that state.

A focused regression test should hold two threads immediately before they try to claim the same order, release them together, and assert that exactly one gateway call and one payment record result. The current implementation produces two of each under the equivalent post-lookup barrier.

The tradeoff is that a process crash or uncertain gateway response can leave an order pending and require reconciliation. A database transaction cannot make a remote charge and a local commit atomic; even a successful charge followed by a failed database update has the same uncertainty. Holding a database lock across the gateway call would serialize overlapping requests but would not eliminate that failure window.
