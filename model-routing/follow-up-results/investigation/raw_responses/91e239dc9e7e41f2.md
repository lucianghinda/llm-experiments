The race is in `Checkout#charge`: it reads the store, then charges the gateway, then inserts a payment. Those are three separate operations. `PaymentStore` synchronizes each lookup and insert individually, but that does not make the whole sequence atomic. The code assumes that a caller which sees no payment is the only caller about to charge that order.

A possible interleaving for order 41:

1. Request A looks up order 41 and finds no payment.
2. Request B looks up order 41 and also finds no payment.
3. Both pass the test seam and call `gateway.charge` with `order-41`.
4. Each inserts a payment row.

The test demonstrates this: the gateway records two charge calls and the store has two payments. The shared key alone does not prevent that in the supplied code; `FakeGateway` merely records keys and gives every call a new charge result.

**Smallest production-worthy correction:** make claiming an order for payment atomic, and enforce uniqueness in the database. Add a unique constraint on `payments.order_id` (if the invariant is one payment per order), then use a transaction or atomic insert/upsert to create or claim the payment before calling the gateway. Only the request that successfully claims it may initiate the charge; the other request should load and follow that payment’s state. A transaction around the current lookup, gateway call, and insert is not sufficient as a general solution: it can hold a database lock across a slow network call, and the external call cannot be rolled back with the database.

The claim needs to represent an in-progress payment as well as a completed one, so a concurrent request can recognize that work is underway. The minimal sketch is a unique payment row with a pending state and a durable provider idempotency key, atomically inserted before the external call. On a uniqueness conflict, the losing request reads that row rather than calling the gateway. After the call, the winner records the result. The supplied store has no payment state or claim operation, so implementing this requires extending it beyond the current `find_by_order`/`insert` API.

For a retry after an uncertain response, reuse the same durable key for the same order and resume or reconcile the existing pending attempt; do not create a fresh attempt merely because the caller did not receive a response. The code constructs a stable-looking key, `order-#{order_id}`, but it neither persists a claim before calling the gateway nor specifies what the gateway does with repeated keys. No provider behavior can be inferred from this reproduction.

A focused regression test would run two threads against the same order, synchronize them after both start, and assert that only one request can claim and call the gateway, with one payment record. Add a retry case in which the first attempt’s outcome is left uncertain and assert that the retry uses the persisted key and does not create a second local claim or independently start another charge. The current barrier test already exposes the defect by expecting two gateway calls; the corrected behavior should make that expectation one.

**Limitation/tradeoff:** a local unique constraint and claim prevent overlapping requests from independently starting work, but they cannot make the database write and an external charge one atomic transaction. If the process fails after the gateway call but before recording its result, the pending attempt needs reconciliation or a retry policy that relies on a documented gateway idempotency contract. The supplied code provides no such contract, so it cannot establish exactly-once charging across that failure window.
