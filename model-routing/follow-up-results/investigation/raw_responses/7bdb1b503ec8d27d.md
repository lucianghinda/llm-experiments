The likely failure is a **check-then-act race** in [Checkout#charge](/workspace/lib/checkout.rb). The store synchronizes each lookup and insert separately, but nothing makes the decision to charge exclusive for an order. The shared `order-41` key does not prevent duplicate calls: `FakeGateway` records every call and has no deduplication behavior.

A concrete execution is:

1. Request A looks up order 41 and finds no payment.
2. Request B looks up order 41 and also finds no payment.
3. Both call the gateway with `order-41`.
4. Both insert a payment record.

The existing [race test](/workspace/test/checkout_test.rb) forces precisely this interleaving and observes two gateway calls and two records.

The smallest durable correction is to **claim the order before calling the gateway**. Insert a payment attempt with a pending state and the stable key, protected by a database **unique constraint on `order_id`**. The insert and ownership decision must be atomic: only the request that successfully creates the claim may initiate the gateway call. A competing request that hits the unique constraint should read the existing attempt and return its completed result or report that it is pending; it must not call the gateway. After a confirmed success, persist the result and mark the attempt complete. The uniqueness constraint is essential even if application code checks first.

For a retry after an uncertain response, look up the same attempt and do not blindly issue another charge. If the gateway call might have succeeded but its result was lost, leave the attempt in an uncertain state for reconciliation. The supplied code states no gateway deduplication or lookup contract, so reusing the same key alone cannot establish that another call is safe. If a real gateway later provides a documented way to query or safely retry by that key, reconciliation can use it.

A focused regression test should start two requests for the same order together, hold the winning request inside the gateway call, and let the other request proceed. Assert that the gateway is called **once** and that there is **one** payment attempt; then release the winner and verify the completed result is available on a subsequent retry. The current implementation fails because both requests can reach the gateway.

The tradeoff is that a crash or timeout around the gateway call can leave a pending or uncertain attempt requiring reconciliation. A database transaction cannot atomically commit both a local record and an external charge under the behavior shown, so the fix prioritizes avoiding a second charge over automatically retrying an ambiguous one.
