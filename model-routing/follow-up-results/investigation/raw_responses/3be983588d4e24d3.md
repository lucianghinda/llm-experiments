The likely failure is the **check-then-charge race** in [checkout.rb](/workspace/lib/checkout.rb:42). Each store operation is synchronized, but the lookup, gateway call, and insert are not one atomic operation.

A concrete execution for order 41 is:

1. Request A looks up order 41 and finds no payment.
2. Request B looks up the same order and also finds no payment.
3. Both call `gateway.charge` with `order-41`.
4. Both insert a payment row.

The supplied `FakeGateway` records both calls; it does not deduplicate them. The existing [test](/workspace/test/checkout_test.rb:5) forces this interleaving and confirms two calls and two rows despite the identical keys.

For a production correction, create a durable payment record **before** contacting the gateway, with a unique database constraint on `order_id`. Atomically insert or claim that record so only one request owns the attempt; overlapping requests must observe the existing record and return its completed result or its pending status, without calling the gateway. Persist the outcome and state transitions transactionally. The unique constraint is essential: an application-level lookup followed by an insert still races. Merely adding the constraint to the current code is too late, because both gateway calls occur before either insert.

If a gateway call times out or the process fails after sending it, mark or retain the attempt as **unknown/pending**. A retry must not blindly issue another charge: it should return that status until the outcome can be reconciled. The same stable key should be retained for the attempt, but the supplied code does not establish that the real gateway honors it, provides lookup, or safely accepts a repeated call.

A focused regression test should start two requests for the same order together, hold the first gateway call open, and let the second proceed. Assert that the gateway was called once, only one payment record exists, and the second request receives a pending result or the eventual completed result. The current implementation fails because both requests reach the gateway.

The tradeoff is availability after an uncertain outcome: without a documented provider deduplication or reconciliation mechanism, the service cannot guarantee both automatic retry and no duplicate charge. Conservatively leaving the payment pending may require manual reconciliation. A database transaction alone cannot atomically commit a remote charge and the local payment record.
