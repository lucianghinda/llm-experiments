The defect is a **check-then-act race**, compounded by recording the payment only after calling the gateway. The supplied test passes and demonstrates two gateway calls and two payment rows for one order.

1. **Unsafe operation and interleaving**

   In [Checkout#charge](/workspace/lib/checkout.rb:48), “no payment found” is treated as permission to charge. The lookup and insert are individually synchronized, but the whole operation is not.

   | Step | Request A | Request B |
   |---|---|---|
   | 1 | Finds no payment for order 41 | |
   | 2 | | Finds no payment for order 41 |
   | 3 | Calls gateway with `order-41` | |
   | 4 | | Calls gateway with `order-41` |
   | 5 | Inserts payment | |
   | 6 | | Inserts another payment |

   Both requests use the same key, but [FakeGateway](/workspace/lib/checkout.rb:35) records every call; it does not deduplicate. The parameter name `idempotency_key` establishes no external guarantee.

2. **Smallest production-worthy correction**

   Create a durable payment-attempt record **before** contacting the gateway, with a database `UNIQUE(order_id)` constraint, a persisted provider key, and a status such as `pending`, `succeeded`, or `unknown`.

   The decision “create this attempt and acquire exclusive permission to send” must be atomic:

   - In a short transaction, attempt an insert with conflict handling. Only the request that inserts the row receives permission to call the gateway.
   - Commit that claim before making the gateway call. A competing request reads the existing attempt and returns its status without charging.
   - After a successful response, persist the result and mark the attempt succeeded in another short transaction.

   For this dependency-free reproduction, an atomic `claim` method under the store’s mutex can model the insert-and-winner decision. Production requires the database constraint to coordinate separate processes.

   A uniqueness constraint on the **current, post-charge insert** is too late: both gateway calls have already happened. Merely wrapping the existing sequence in a transaction also does not provide safe recovery from an external charge followed by rollback.

3. **Uncertain responses and regression test**

   A retry of a succeeded attempt returns the stored result. A retry of a pending or unknown attempt returns that status and **does not issue another charge**. If the gateway times out, or the process dies after sending but before saving success, preserve the claim. An existing row must no longer automatically mean “payment succeeded.”

   Reconcile an uncertain attempt before allowing another charge. The supplied code provides neither a reconciliation API nor a deduplication guarantee, so automatic safe resubmission cannot be justified.

   Adapt the existing barrier test: hold both requests after their initial lookup, then release both to the new atomic claim operation. Assert:
   - Exactly one gateway call.
   - Exactly one attempt row, ultimately succeeded.
   - Both responses identify the same attempt; the overlapping loser may report pending.
   - A subsequent retry returns the stored success without increasing the gateway-call count.

   This deterministically distinguishes the current defect from the correction without timing-dependent sleeps.

4. **Limitation**

   This fix favors avoiding duplicate charges over automatic progress. A crash after committing the claim but before sending can leave an uncharged order pending, indistinguishable locally from a charge whose response was lost. Expiring the claim and blindly resending would restore the duplicate-charge risk. Fully automatic recovery requires an additional, verified provider contract or reconciliation mechanism; a local database transaction alone cannot make the external charge and local result commit atomic.
