The defect is a **check-then-act race** in [Checkout#charge](/workspace/lib/checkout.rb:48). Individually synchronized store methods do not make the whole operation atomic. The existing test passes while explicitly demonstrating two gateway calls and two payment records.

1. **Concrete interleaving**

   | Step | Request A | Request B |
   |---|---|---|
   | 1 | Lookup returns no payment | |
   | 2 | | Lookup returns no payment |
   | 3 | Calls gateway with `order-41` | |
   | 4 | | Calls gateway with `order-41` |
   | 5 | Inserts payment | |
   | 6 | | Inserts another payment |

   Both callers assume that observing no payment grants permission to charge. The identical key does not establish safety: [FakeGateway#charge](/workspace/lib/checkout.rb:35) records every call and performs no deduplication.

2. **Smallest production-worthy correction**

   Persist a durable payment attempt **before** calling the gateway, with a unique, non-null database constraint on `order_id`, plus a status such as `in_progress`, `succeeded`, or `unknown`.

   Atomically insert-or-find that attempt and determine whether this request created it. Commit that transaction before contacting the gateway. **Only the creator may call the gateway**; overlapping requests return the existing attempt’s status or completed result.

   After a successful gateway response, persist its result and mark the attempt succeeded in a second transaction. In this reproduction, the claim operation would require one mutex-protected check-and-insert; production requires database enforcement across processes.

   Adding uniqueness only to the current final insert is insufficient: both gateway calls have already happened. A transaction around the existing code also does not by itself make a missing-row lookup exclusive.

3. **Retries and a focused regression test**

   A retry for a succeeded attempt returns the stored result. A retry for an in-progress or uncertain attempt returns its status without issuing another charge. Keep the same durable attempt and key. A timeout or crash after dispatch must not cause automatic deletion or reclamation of that attempt.

   Use one deterministic overlap test: pause request A inside the gateway after recording its call but before returning. Start request B for the same order and let it finish; it must observe the in-progress attempt without calling the gateway. Release A, then retry checkout again. Assert **one gateway call, one attempt row, and the stored successful result on retry**. The supplied implementation makes a second gateway call while A is paused.

4. **Limitation**

   This correction prevents overlapping requests from dispatching twice, but cannot guarantee eventual completion after an uncertain gateway outcome. A crash immediately before dispatch and a crash immediately after a successful charge can leave the same local state. Without a stated provider deduplication or reconciliation contract, automatically retrying risks another charge; withholding retries can leave an order pending for manual reconciliation. A local database transaction cannot remove that ambiguity.
