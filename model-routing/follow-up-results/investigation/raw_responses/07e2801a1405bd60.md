The defect is a **check-then-act race**: finding no payment does not give a request exclusive permission to charge. The existing test confirms this: it passes by asserting two gateway calls and two payment records.

1. **Concrete interleaving**

   In [Checkout#charge](/workspace/lib/checkout.rb:48):

   | Step | Request A | Request B |
   |---|---|---|
   | 1 | Looks up order 41; finds nothing | |
   | 2 | | Looks up order 41; finds nothing |
   | 3 | Calls gateway with `order-41` | |
   | 4 | | Calls gateway with `order-41` |
   | 5 | Inserts payment | |
   | 6 | | Inserts another payment |

   Each store method has a mutex, but the overall operation does not. The stable key offers no demonstrated protection: [FakeGateway#charge](/workspace/lib/checkout.rb:35) records every call, including repeated keys.

2. **Smallest production-worthy correction**

   Persist a payment attempt **before** calling the gateway, with a database `UNIQUE NOT NULL` constraint on `order_id`, a stored provider key, and an explicit status such as `pending`, `succeeded`, or `unknown`.

   The atomic operation must be **claiming the order and deciding which request owns permission to call the gateway**:

   - Insert and commit a `pending` attempt using the unique constraint.
   - Only the request whose insert succeeds may call the gateway.
   - A conflicting request reads the existing attempt and returns its status/result without charging.
   - After a successful gateway response, persist `succeeded` and the returned charge identifier. An ambiguous failure leaves the attempt unresolved.

   In this reproduction, the equivalent is one mutex-protected `claim` method returning both the attempt and whether it was newly created. In production, database uniqueness must enforce this across processes.

   Adding uniqueness only to the existing final insert is too late: both gateway calls have already occurred. Likewise, wrapping the existing code in an ordinary transaction does not by itself serialize two lookups of an absent row.

3. **Retries and regression test**

   A retry after a lost response should return the stored successful result, or report the existing attempt as pending/unknown. It must not automatically submit another charge for an unresolved attempt. Reusing the key alone is insufficient under the supplied gateway behavior.

   One focused regression test should block the first request inside the gateway after recording its call, then start a second request for the same order. Assert that the second request observes the existing pending attempt and that the gateway call count remains **one**. Release the first request, then retry again and assert the stored successful result is returned with one attempt and still one gateway call. Use queues/barriers, not sleeps.

4. **Limitation**

   The database and gateway cannot commit atomically here. A crash after committing the claim but before sending the charge can leave an uncharged order pending; a crash after charging but before recording success can leave a charged order unknown. Preserving the claim prevents duplicate submissions but requires reconciliation to restore progress. Safe automatic resubmission would require a verified provider deduplication or lookup contract that this code does not supply.
