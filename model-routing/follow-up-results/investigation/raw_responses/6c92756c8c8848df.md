The defect is a **check-then-act race**, compounded by recording the payment only after calling the gateway. The supplied test passes because it explicitly expects two gateway calls and two payment records.

1. **Unsafe operation and interleaving**

   In [Checkout#charge](/workspace/lib/checkout.rb:48), finding no payment is treated as permission to charge. Individual store methods are synchronized, but the whole sequence is not:

   | Step | Request A | Request B |
   |---|---|---|
   | 1 | Lookup order 41 → absent | |
   | 2 | | Lookup order 41 → absent |
   | 3 | Call gateway with `order-41` | |
   | 4 | | Call gateway with `order-41` |
   | 5 | Insert payment | |
   | 6 | | Insert payment |

   Both use the same key, but [FakeGateway#charge](/workspace/lib/checkout.rb:35) unconditionally records every invocation. The argument name `idempotency_key` establishes no deduplication guarantee.

2. **Smallest production-worthy correction**

   **Atomically reserve the order before any gateway call**, and persist that reservation before contacting the gateway.

   Add a payment-attempt status, stored gateway result, and a database `UNIQUE NOT NULL` constraint on `order_id`. In a short transaction, attempt to insert an `in_progress` record with the stable provider key. Only the request that successfully creates and commits that record may call the gateway. A conflicting request reads the existing attempt and returns its result or pending status; it must not charge.

   After a successful gateway response, update that same record to `succeeded` and persist the returned result in another short transaction. In this dependency-free reproduction, implement reservation as one mutex-protected find-and-insert operation that also returns whether the caller created it.

   A uniqueness constraint applied only to the current **post-charge insert** is too late: both gateway calls have already happened. Similarly, rolling back a database transaction cannot undo a gateway charge.

3. **Uncertain responses and regression test**

   If the client loses the checkout response after success was persisted, its retry returns the stored success. If the gateway response is lost, or the process crashes between charging and recording success, leave the attempt pending/unknown. Retries must return that state without issuing another charge. Reconcile before permitting another attempt; neither automatic replay safety nor a reconciliation API is established by this code.

   Adapt the [existing barrier test](/workspace/test/checkout_test.rb:5): hold both requests after their initial absent lookup, then release them to compete for the atomic reservation. Assert **one gateway invocation, one payment-attempt record, and eventual success on that record**. Retry after both threads finish and assert the stored success is returned with the gateway count still one. This deterministically fails against the original implementation.

4. **Limitation**

   This trades automatic recovery for duplicate prevention. A crash after reservation but before charging can leave an order unresolved even though no charge occurred. Do not automatically expire the reservation and charge again: the same unresolved state can also mean a charge occurred but its response was lost. Safe automatic recovery requires an additional, explicit provider guarantee or authoritative reconciliation mechanism. The supplied code supports neither, so an exactly-once external charge cannot be promised.
